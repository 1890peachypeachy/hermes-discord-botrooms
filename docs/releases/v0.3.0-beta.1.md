# v0.3.0 beta 1 release and upgrade notes

This beta changes a configured Discord channel from one continuing conversation
into a launcher for independent Bot Rooms.

- A top-level message creates a new Discord thread with fresh agent context.
- A reply inside that thread continues only that room.
- Several threads can run independently in the same configured channel.
- Parent-channel status can summarize them without allowing an ambiguous
  command to mutate one.

The release remains a beta because it requires a compatible Hermes build. Run
the compatibility probe and plugin doctor before installation.

## Upgrade impact for v0.2 users

The first participating gateway to open the shared room database performs a
one-time migration.

| Reset or retired for Discord rooms | Preserved |
| --- | --- |
| Unfinished runs are marked stopped | Room configuration and profile selection |
| Pending approvals and clarification prompts | Discord message and event records |
| Member holds | Delivery records and cached attachment files |
| Reuse of old room-wide model sessions | Completed run history and visible Discord history |
| Model context before each existing thread's migration boundary | Non-Discord room state |

The next human message in an existing thread therefore starts from fresh agent
context even though its older Discord messages remain visible. New top-level
messages create new isolated threads as normal. Non-Discord room state is
carried forward.

Migration is transactional and serialized across gateway processes. If it
cannot complete, it rolls back instead of marking a partial migration as done.

## Upgrade checklist

1. Confirm no important Bot Room run or approval is still active.
2. Record the selected profiles, connected Discord identities, active plugin
   revision, Hermes runtime ownership, and configured room IDs.
3. Stop the participating gateways and make a recoverable copy of
   `<hermes-root>/plugin-data/hermes-discord-botrooms/`.
4. Check out the exact clean Bot Rooms commit to install. Run:

   ```bash
   python -m hermes_discord_botrooms.compat --json
   hermes plugins doctor . --ci
   ```

5. Install that exact commit into the controlling profile. Rebuild the explicit
   non-interactive setup command from the values recorded in step 2, following
   [Manual installation](../manual-install.md#configure-a-room), and run it with
   `--dry-run --json`. Verify that its profiles, controller, server, channel,
   install commands, and restart commands are unchanged except for the plugin
   revision.
6. Apply the same explicit command without `--dry-run`. This installs the same
   pinned revision for every selected profile and restarts those gateways.
   Repeat the preview and apply steps for each configured room.
7. Run:

   ```bash
   hermes botrooms doctor --live --json
   hermes botrooms list --json
   hermes botrooms status --json
   ```

8. Complete the [live acceptance checklist](../operations.md#live-acceptance-checklist),
   including two top-level messages and a follow-up inside each resulting
   thread.

Do not leave participating profiles on different plugin revisions. A connected
gateway proves only that Discord transport started; the two-thread acceptance
test proves the new room boundary works.

If acceptance fails and the v0.2 state must be recovered, follow
[Restore a pre-upgrade state backup](../operations.md#restore-a-pre-upgrade-state-backup).
